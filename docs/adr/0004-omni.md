# ADR-0004: Omni — running Sidero's fleet control plane, not its single-binary demo

## Status

Proposed (2026-08-02). Depends on [ADR-0001](0001-layering-on-core.md) and
[ADR-0002](0002-identity.md) (both of ADR-0002's Core dependencies have shipped — see its
Status section). Does not depend on [ADR-0003](0003-secrets-and-pki.md): Omni is
backend-agnostic about its own secrets (decision 8), so nothing here waits on ADR-0003's ESO/
OpenBao work — that work is for downstream clusters' own secrets, a problem ADR-0006 owns, not
this ADR. Blocks ADR-0006 (downstream provisioning) and is referenced by ADR-0007 (Manager's
own state, which owns backing up Omni's etcd).

This ADR corrects a detail in ADR-0002: its prose and frontmatter describe Omni's client as a
`KeycloakOIDCClient`. Decision 2 below explains why that's wrong for RBAC purposes and picks
`KeycloakSAMLClient` instead. ADR-0002 should be updated to match once this merges.

## Context

The roadmap states this ADR's job in one line: *"Pro deployment rather than the
single-binary demo: etcd, storage, TLS and SANs, SideroLink exposure, auth against
Keycloak."* Each clause names a real decision, because Omni — unlike everything else Manager
has built so far — is a third-party product Manager deploys and configures, not a Windsor
facet composing Core primitives from scratch.

**Omni ships two genuinely different shapes.** The single-binary demo (`omnictl demo` /
`docker run ghcr.io/siderolabs/omni`) keeps its state in memory or a local file with no etcd,
convenient for kicking the tires but unusable as a fleet's system of record — a restart loses
every managed cluster's identity. The self-hosted deployment, via Sidero's official Helm chart
(`siderolabs/omni` `deploy/helm/omni`), is the real product: embedded or external etcd,
persistent storage, TLS-terminated API/kube-proxy/SideroLink endpoints, a WireGuard-exposed
SideroLink service, and pluggable Auth0/SAML/OIDC authentication. A fleet's control plane is
the Helm-chart shape or nothing; the demo never enters consideration.

**Manager already anticipated this facet's shape.** `config-provisioning.yaml`'s
`provisioning` facet turns on `identity` and `image_factory` together specifically because,
in its own words, *"Omni authenticates operators against the cluster identity provider and
provisions Talos machines from the image factory."* Omni is the first real consumer of both:
the self-hosted `image-factory` facet ([addon-image-factory.yaml](../../contexts/_template/facets/addon-image-factory.yaml))
already hosts schematics and boot assets that Omni should pull from instead of the public
`factory.talos.dev`, and Core's `identity` capability ([ADR-0002](0002-identity.md)) already
ships a realm Omni can authenticate against. Naming Manager's own facet `addon-omni.yaml` was
even used as ADR-0001's own worked example of "a Manager facet landing after every Core
facet" — this ADR is that facet's design, not a new naming question.

**etcd and storage.** Sidero's own hardware guidance says small and medium deployments can
safely share a host with embedded etcd as long as the disk has good IOPS and enough capacity;
larger deployments split etcd onto its own machines. The Helm chart's default is embedded
etcd on a single PVC (`persistence.enabled: true`, 16Gi+ recommended, `ReadWriteOnce`), with
external etcd as an opt-in for HA. There is one management cluster and one fleet today — the
same "one tenant" reasoning ADR-0002 used to defer a separate realm applies here.

**TLS and SANs.** Omni's Helm chart terminates TLS itself at three separate advertised
endpoints — the main API/UI, the Kubernetes proxy, and the SideroLink API — each needing a
cert whose SANs match its `ingress.*.host`. This is unlike Keycloak or Grafana, which
terminate at Core's shared gateway and serve plain HTTP behind it: Omni's SideroLink traffic
is a raw WireGuard tunnel and its machine-join/event-sink paths are gRPC, neither of which fit
the shared HTTP(S) gateway's model. Omni needs its own certificates, not a gateway route.

**SideroLink exposure.** Downstream Talos machines dial Omni directly over WireGuard to
establish SideroLink — a purpose-built peer-to-peer tunnel, not proxied through any gateway.
The Helm chart's `service.wireguard` block wants a `NodePort` or `LoadBalancer` Service with a
stable, publicly reachable `advertisedEndpoint` (`host:port`) baked into every machine's join
config. Getting that endpoint wrong after machines have joined means re-provisioning them —
this is a value downstream Talos configuration depends on for the life of the cluster, so it
belongs in the same category ADR-0002 decision 8 gives the OIDC issuer: a stable contract
downstream config consumes.

**Auth against Keycloak has a real gap to design around.** Omni supports Auth0, SAML, and
OIDC, exactly one enabled at a time. ADR-0002's own prose assumed Manager would add a
`KeycloakOIDCClient` for Omni, the same CR type Core uses for Grafana. But Omni's OIDC
provider has no mechanism today to map an identity provider's group or role claims onto
Omni's own access control — that's an open, unimplemented feature request upstream
([siderolabs/omni#2596](https://github.com/siderolabs/omni/issues/2596)). Omni's SAML
provider, by contrast, already supports exactly this: IdP attributes map to Omni user labels
via a `saml.omni.sidero.dev/` prefix, and `AccessPolicy` label selectors consume those labels
to grant roles. Keycloak's operator already vendors `KeycloakSAMLClient` alongside
`KeycloakOIDCClient` (ADR-0002's Context section), so nothing new needs building on the
identity side — Manager just points Omni at the client type that actually has the mapping
Manager needs.

## Decision

**1. Manager deploys Omni via its official Helm chart, in a new facet `addon-omni.yaml`, not
the single-binary demo.** The demo's ephemeral state disqualifies it outright for a fleet
control plane — this isn't a cost/complexity tradeoff, it's a correctness one. The facet
follows ADR-0001's mechanics: it turns on `identity` and `image_factory` through
`provisioning.enabled` (already wired in `config-provisioning.yaml`) rather than redeclaring
either, and it takes component names Core does not use.

**2. Manager clients Omni into the platform realm with a `KeycloakSAMLClient`, not a
`KeycloakOIDCClient`.** This corrects ADR-0002's assumption. SAML is the only one of Omni's
identity-provider integrations with a working group-to-role mapping today
(`saml.omni.sidero.dev/` labels feeding `AccessPolicy` selectors); using Keycloak's OIDC
client for Omni would authenticate operators but leave every one of them unable to get a role
beyond whatever Omni's default grants. **The OIDC client is the named successor**: the day
`siderolabs/omni#2596` ships claim-mapping for OIDC, this decision is revisited, not worked
around — Manager would rather run one consistent client type across every consumer than carry
a permanent SAML/OIDC split for no reason beyond upstream timing.

**3. etcd is embedded on a single PVC for v0.1.0; external etcd is the topology: ha
successor.** One tenant, one management cluster — Sidero's own guidance says a well-performing
disk is enough at this scale, and splitting etcd out before there's a second control-plane
node to justify it is bootstrap Manager would carry for no isolation anyone needs yet. The
same `topology: ha` knob Core's own `identity` and `database` facets already read decides
this the same way: `topology: ha` moves Omni to external etcd and however many control-plane
replicas the chart supports; the single-node default doesn't.

**4. TLS terminates at Omni itself, issued by Core's `pki` `public-acme` ClusterIssuer, not
the shared gateway.** Omni's three advertised endpoints need certs whose SANs downstream
Talos machines and operator browsers both trust without extra configuration — the same
zero-config reasoning ADR-0002 decision 4 uses for the OIDC issuer's public certificate.
cert-manager (Core's `pki` addon) issues the certs; Omni's Helm values reference the resulting
Secrets directly (`ingress.*.tls`) rather than going through a gateway `HTTPRoute`, because
SideroLink and Omni's gRPC/kube-proxy paths don't fit the HTTP(S) gateway's model. The
private-PKI alternative is deferred the same place ADR-0002 deferred it — to ADR-0003, which
owns Manager's own root.

**5. SideroLink gets its own `LoadBalancer` (or `NodePort` where a load balancer isn't
available) Service, separate from the shared gateway, with a stable advertised
`host:port`.** Downstream Talos machines dial this address directly over WireGuard; it isn't
proxied traffic the gateway can front. Manager's facet derives the advertised endpoint from
the same `dns.public_domain || dns.private_domain` config ADR-0002's issuer derivation already
reads, keeping one source of truth for the fleet's externally reachable name.

**6. Omni points at Manager's self-hosted image factory, not `factory.talos.dev`.** The
exact Omni-side config key needs confirming against the Helm chart's `config.yaml` schema at
implementation time — Sidero's on-prem image-factory docs cover the factory side
(`http.externalURL`) but not the Omni-side pointer as of this writing — but the intent is firm:
a fleet that already runs `addon-image-factory` for its own schematics has no reason to depend
on a public factory for the clusters it provisions. This is the same "reuse what Manager
already built" reasoning as decisions 1 and 2.

**7. Bootstrap admins are a dev-only allowlist, the same shape Core's `dev-user` pattern
uses.** `config.auth.initialUsers` seeds an initial admin email list — useful for standing up
a fresh Omni before any operator has signed in through Keycloak, gated the same way Core gates
its own dev realm user (`dev == true`). Real operator access routes through decision 2's SAML
client and Keycloak group membership; the allowlist isn't how production access is granted.

**8. None of Omni's own secrets are blocked on ADR-0003 — Omni is backend-agnostic and each one
already has a permanent home.** Omni's Helm chart reads plain Kubernetes Secrets (`certFile`/
`keyFile` paths, a mounted `clientSecret`); it has no native awareness of Vault, OpenBao, or
ESO, and nothing about switching backends would change what Omni does with the Secret once
it's there. Concretely: the etcd encryption key is a Terraform-generated secret in the
facet's own `secrets:` block, the same mechanism `addon-image-factory`'s cache-signing key
already uses — a bootstrap value with no rotation story, not an interim waiting to be
replaced. TLS keys come from cert-manager, which already issues and rotates them live — no
ESO involved. The SAML client secret is generated and written by the Keycloak operator, read
via `valueFrom` (ADR-0002 decision 3) — also no ESO involved. ADR-0003's ESO/OpenBao work is
for a different problem entirely: giving *downstream* clusters' own ESO instances (installed
on every cluster per `core#2284`) a runtime secrets backend to reach across the cluster
boundary for their own workloads. That's not something Omni's facet needs to build or wait
on — it's ADR-0003's and ADR-0006's problem, not this ADR's.

## Consequences

- Omni is the first Manager facet with a stateful, non-Core-composed backing service of its
  own (etcd) rather than a thin client or config-turning-on layer — the closest precedent is
  Core's own CloudNativePG-backed addons, not anything Manager has authored before.
- **This ADR corrects ADR-0002.** Its description and decision 2 name Omni's client as a
  `KeycloakOIDCClient`; that should read `KeycloakSAMLClient` once this ADR exists, with a
  pointer here for the reasoning. This is a documentation-only fix — ADR-0002 built nothing,
  so there's no code to change.
- Choosing SAML over OIDC for Omni specifically means Manager's identity facets are not
  uniform across consumers: Grafana (Core's) is OIDC, Omni (Manager's) is SAML, and a future
  fleet dashboard or fleet API picks whichever of the two actually has the RBAC mapping it
  needs at the time it's built. Decision 2 names the reunification trigger (upstream OIDC
  claim mapping) so this isn't a permanent, undocumented split.
- The embedded-etcd default in decision 3 means Omni's data durability rests on one PVC's
  storage class and one node's availability until `topology: ha` is set — the same
  single-point-of-failure the roadmap's open HA question already flags for the whole
  management cluster. ADR-0007 owns backing that PVC up regardless of topology.
- Decision 4's public-certificate default carries the same disconnected-install deferral
  ADR-0002 already named for the OIDC issuer: a private-only deployment has no ACME path and
  waits on ADR-0003's CA-distribution work.
- Decision 6 is the one open implementation detail this ADR doesn't fully close — the actual
  Omni-side config key pointing at a self-hosted image factory needs confirming against the
  Helm chart before `addon-omni.yaml` is written. That's an implementation task, not a
  decision this ADR is missing: the direction (self-hosted factory, not the public one) is
  firm regardless of the exact key name.
- Omni now sits on ADR-0002's critical path from the other direction: Core's realm and
  Manager's SAML client must both exist before an operator can sign into Omni at all, and
  every downstream cluster Omni provisions depends on Omni being reachable. A slow or failed
  Omni converge blocks fleet provisioning entirely, not just its own namespace.

## Alternatives considered

**Run Omni's single-binary demo behind Manager's own persistence layer (e.g., back its data
directory with a PVC).** Rejected: the demo's in-memory/local-file state model isn't designed
for external durability, and Sidero ships a real self-hosted path specifically for this use
case — working around the demo's limitations would mean maintaining a configuration Sidero
doesn't support and doesn't test, for no benefit over the supported chart.

**Use Auth0 instead of Keycloak for Omni's auth.** Omni's most-documented auth path. Rejected
under [ADR-0001](0001-layering-on-core.md) rule 1, the same way ADR-0002's alternatives
rejected trusting a cloud IdP directly: it doesn't work on metal or Hetzner, and it fragments
operator identity across two providers when Core already hosts one hardened realm every other
management service authenticates against.

**Wait for upstream OIDC claim-mapping support rather than using SAML now.** Would keep
Manager's client types uniform from day one. Rejected as an open-ended wait on someone else's
roadmap for a feature request with no committed timeline — SAML is fully supported today, the
CRD is already vendored, and decision 2 names the exact trigger for revisiting rather than
leaving Omni's auth unbuilt indefinitely.

**External etcd from the start, skipping the embedded default.** Would remove the single-node
storage risk decision 3 accepts. Rejected as premature for the same one-tenant reasoning
ADR-0002 used to defer a separate realm: an external etcd cluster is infrastructure to
provision, secure, and back up before there's a second control-plane node that actually needs
it, and `topology: ha` is already the named successor the moment that changes.
